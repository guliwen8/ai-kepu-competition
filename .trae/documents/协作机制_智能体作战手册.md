# 智能体协作机制（项目作战手册）

## 目标
- 用户只做最终验收确认；需求澄清与中间推进默认由系统自驱完成
- 任何变更都经过自动门禁与交叉审核，避免“写完才发现不可跑/不可用”
- 以可运行闭环为单位交付：每个里程碑都能用冒烟脚本与页面操作验证

## 团队编组（可用智能体一览）
以下均为本项目可调用的智能体/能力，按“输入 → 输出”执行，不需要用户逐条下指令。

### 1) 总控（Coordinator）
- 责任：拆解目标、派发任务、合并交付物、把关里程碑、对外汇报
- 输入：当前仓库、计划文档、已落地功能、用户最终验收口径
- 输出：里程碑计划、任务看板、合并后的可运行版本、发布说明
- 完成标准：门禁全绿 + 文档齐全 + 验收用例通过

### 2) 侦察（Search Scout）
- 责任：快速定位代码入口、影响面、复用点；提供变更清单与风险
- 输出：文件清单、调用链、需要改的 DTO/API/页面、回归点
- 对接标准：给出可点击代码引用与“建议修改点”

### 3) 后端架构（Backend Architect）
- 责任：领域模型/Prisma 设计、API 设计、权限与数据隔离策略
- 输出：schema/迁移策略、控制器/服务实现、接口契约、错误码与幂等规则
- 对接标准：Swagger 可见 + 脚本可测 + 数据库约束明确

### 4) 问题终结者（Bug Terminator）
- 责任：对运行时报错、构建失败、不可复现问题做根因定位与修复
- 输出：最小复现、根因说明、修复补丁、回归验证命令
- 对接标准：给出“如何确认已修复”的可执行步骤

### 5) 质量保障（QA Engineer）
- 责任：用例分层、质量门禁、回归策略、缺陷分级、发布检查单
- 输出：P0 用例与门禁、回归包、缺陷分级规则、发布 checklist
- 对接标准：每个里程碑至少有 1 条自动化 E2E 覆盖主链路

### 6) DevOps/交付（DevOps Deployment Expert）
- 责任：CI/CD、环境隔离、监控预警、自动化流转与阻断策略
- 输出：GitHub Actions、分支保护建议、失败预警（Issue/PR 评论）、发布流水线
- 对接标准：PR 未通过门禁不可合并；main 失败自动预警

### 7) 文档与对外（Technical Writer）
- 责任：把系统“怎么用/怎么部署/怎么排障”写清楚
- 输出：README/运行手册/发布说明/API 使用指南
- 对接标准：新能力必须配套“操作路径 + 失败排查”

### 8) 代码审计（Code Reviewer）
- 责任：安全/性能/可维护性审查，防止引入隐患
- 输出：风险清单、修正建议、必须改/可改项
- 对接标准：P0 风险（越权/泄露/数据破坏）必须在合并前清零

## 交付物标准（模板与对接）
所有模块的交付必须包含如下“最小集合”，以便自动承接与交叉审核。

### A. 需求/规格（Spec）
- 位置：`.trae/documents/`
- 内容必须包含：目标、非目标、用户路径、数据结构、接口、边界与失败态

### B. 代码交付（Implementation）
- 必须通过：`typecheck`、对应 workspace 的 `build`
- 接口变更必须同步：Swagger（或 OpenAPI）与前端调用处

### C. 验证交付（Verification）
- 必须提供“可一键执行”的验证命令（本项目以 smoke 为基准）
- 至少覆盖：成功路径 + 1 条失败路径（如越权/校验失败/锁定后不可改）

### D. 变更说明（Changelog）
- 说明：新增/变更/删除、兼容性、迁移要求、回滚方式

## 自动协同流转机制（无需人工协调）
### 1) 任务承接
- 总控根据里程碑生成任务看板（见 `.trae/documents/执行计划_全流程自主推进.md`）
- 每个任务都定义：输入、输出、验收、回归点

### 2) 进度同步
- 所有交付以“可运行版本”为准：每完成一块即让门禁跑绿，并更新里程碑状态
- 里程碑状态仅有三种：进行中/可验收/已完成

### 3) 问题预警
- PR 门禁失败：自动阻断合并并在 PR 里给出失败原因
- main/nightly 失败：自动创建 Issue 作为预警与追踪入口

### 4) 自动交叉审核（质量内循环）
- 规则：实现者不能自审通过
- 顺序：实现完成 → Code Review → QA 门禁 → 合并/发布
- 触发：门禁绿后自动进入下一个阶段（失败则回滚到“实现/修复”）

## “用户零介入”的默认约定
- 默认继续推进：除非遇到会影响产品方向的不可逆决策（如评分规则、赛制轮次）
- 默认取最小可用方案：先保证闭环跑通，再增强可配置与运营能力
- 用户仅在两个时点参与：
  - 最终验收：按验收清单确认可用
  - 重大决策：出现多个互斥方案且会影响数据模型/流程时
