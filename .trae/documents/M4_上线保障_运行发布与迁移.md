# M4｜上线保障：运行、监控、发布与迁移

## 本地运行（推荐顺序）

- 启动基础设施（Postgres/Redis）：
  - `npm run infra:up`
- 启动 API（开发）：
  - `npm -w api run dev`
- 启动后台（开发）：
  - `npm -w admin-web run dev`
- 小程序（WeChat 小程序 dist 输出）：
  - `npm run miniapp:dev:weapp`

## 监控（本地 Prometheus）

- 前提：本机已启动 API，且 `http://localhost:3001/metrics` 可访问
- 启动 Prometheus：
  - `npm run monitoring:up`
- 打开：
  - `http://localhost:9090`
- 默认已配置采集目标：
  - `host.docker.internal:3001/metrics`（macOS/Windows Docker Desktop 适用）

## 告警（Alertmanager）

- Alertmanager 地址：
  - `http://localhost:9093`
- 默认 receiver：
  - `monitoring/alertmanager.yml`（webhook）
- 本地接收示例：
  - `npm run monitoring:webhook`（监听 `http://localhost:18080/alertmanager`）
  - 触发告警后会在控制台输出 alertname 摘要

## 告警规则（Prometheus rules）

- 文件：
  - `monitoring/alerts.yml`
- 当前内置规则：
  - ApiDown：`up{job="api"}==0`
  - ApiHigh5xx：5xx 速率持续升高
  - ApiHighLatencyAvgMs：平均延迟 > 1s
  - ApiDbHighLatencyAvgMs：数据库平均查询延迟 > 200ms
  - ApiDbSlowQueries：出现 >=500ms 的慢查询

## 数据库迁移（Prisma）

### 生产/预发：推荐 migrate deploy

- 生成客户端：
  - `npm -w api run prisma:generate`
- 执行迁移：
  - `npm -w api exec -- prisma migrate deploy`

### 迁移原则（避免不可回滚事故）

- 默认采用“向前兼容”的 schema 变更：
  - 新增字段先允许 null / 先不加强校验
  - 写入新字段灰度后，再做 not null/约束收紧
- 避免在同一次发布内做“删除字段/改语义”的不可逆操作

## 备份与恢复（Postgres）

- 备份：
  - `pg_dump "$DATABASE_URL" --format=custom --file backup.dump`
- 恢复：
  - `pg_restore --clean --if-exists --dbname "$DATABASE_URL" backup.dump`

## 发布流程（GitHub Actions）

### 产物与 Release（Draft）

- 推 tag（示例）：
  - `git tag v1.0.0 && git push origin v1.0.0`
- workflow：`.github/workflows/release.yml`
  - 生成 Draft Release，并上传打包产物：
    - `api-<tag>.tgz`
    - `admin-web-<tag>.tgz`
    - `miniapp-<tag>.tgz`
    - `deploy-<tag>.tgz`（标准化部署/回滚脚本）

### 部署（Production）

- 发布 Draft Release（Publish）后触发：
  - workflow：`.github/workflows/deploy-production.yml`
- 依赖 GitHub Environments + Secrets（未配置会自动跳过）
  - `production` environment 建议开启 Required reviewers
  - `PROD_DEPLOY_PATH`（默认 `/opt/aikepu/releases`）
  - 服务器侧约定目录：
    - `${PROD_DEPLOY_PATH}/<tag>/`：每次 release 上传的版本目录
    - `${PROD_DEPLOY_PATH}/current`：指向当前生效版本目录的软链
  - 可选 hooks（在服务器上创建）：
    - `${PROD_DEPLOY_PATH}/hooks/before-deploy.sh`
    - `${PROD_DEPLOY_PATH}/hooks/after-deploy.sh`
  - 样例脚本：
    - `scripts/deploy/examples/systemd-after-deploy.sh`
    - `scripts/deploy/examples/pm2-after-deploy.sh`

### 预发（Staging）

- main 分支 checks + api-regression 通过后触发：
  - workflow：`.github/workflows/ci-main.yml` 中的 `deploy-staging`
- 依赖 GitHub Environments + Secrets（未配置会自动跳过）
  - `STAGING_DEPLOY_PATH`（默认 `/opt/aikepu/releases`）
  - `STAGING_API_BASE_URL`（用于部署后 `/healthz` 校验）
  - 服务器侧目录与 production 相同：
    - `${STAGING_DEPLOY_PATH}/<sha>/`
    - `${STAGING_DEPLOY_PATH}/current`
  - 可选 hooks（在服务器上创建）：
    - `${STAGING_DEPLOY_PATH}/hooks/before-deploy.sh`
    - `${STAGING_DEPLOY_PATH}/hooks/after-deploy.sh`
  - 样例脚本与 production 共用

### 回滚（按 tag 一键回滚）

- workflow：`.github/workflows/rollback.yml`
- 选择环境 + tag，重新部署历史 Release 的产物
  - 可选 hooks（在服务器上创建）：
    - `${DEPLOY_PATH}/hooks/before-rollback.sh`
    - `${DEPLOY_PATH}/hooks/after-rollback.sh`

## 外部健康检查（staging/production）

- workflow：`.github/workflows/health-external.yml`
- 依赖 Secrets：
  - `STAGING_API_BASE_URL`
  - `PROD_API_BASE_URL`
- 失败行为：
  - 自动创建 issue（用于替代“告警通知”在你们还未接入 IM webhook 的阶段）
