# 质量门禁与交叉审核

## 放行原则

- 任何阶段合并/发布必须满足：门禁全绿 + P0 缺陷为 0
- 门禁失败即阻断，不允许“先合后修”

## 门禁分层（Gate）

### Gate-0（提交/PR：静态门禁）

- `npm run format:check`
- `npm run lint`
- `npm run typecheck`
- `npm run build`

### Gate-1（后端主链路 E2E）

- `npm -w api run smoke`
- `npm -w api run admin:smoke`
- `npm -w api run judging:smoke`

### Gate-2（UI 冒烟）

- admin-web：登录 → 仪表盘 → 复核台列表/详情 → 评审管理 → 评委打分页
- miniapp：登录 → 提交作品 → 我的作品列表/详情

## 缺陷分级（Severity）

- S0：主链路不可用/越权/数据破坏/敏感信息泄露
- S1：主链路可走但结果错误/高频崩溃/导出错误
- S2：非主链路功能异常/明显 UI 问题但可绕过
- S3：文案/轻微体验问题

## 交叉审核流程（自动内循环）

### 1) 实现者提交

- 交付包含：Spec（如有）、代码、验证命令、变更说明

### 2) Code Review（安全/性能/可维护性）

- 检查点：鉴权、越权、输入校验、幂等、日志不泄露敏感信息
- P0 风险必须在合并前清零

### 3) QA 复核（门禁+用例）

- 必跑 Gate-0/Gate-1
- 关键 UI 冒烟抽检 5 分钟内完成

### 4) 合并与回归

- main 合并后自动跑回归（nightly/主分支门禁）
- 失败自动预警并阻断后续稳定基线

## 发布前检查单（Pre-Release）

- 依赖服务：PostgreSQL/Redis 正常
- 配置：`ADMIN_BOOTSTRAP_TOKEN` 等关键环境变量齐全
- 数据库：迁移/回滚方案明确
- 门禁：Gate-0/Gate-1 全绿
- 抽检：关键 UI 冒烟通过
